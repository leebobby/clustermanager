> 本文是对整个代码库的通读梳理，面向「刚接手这个项目、需要快速搞清楚它做了什么、
> 哪些能用、哪些还是空壳」的读者。
>
> 与 `README.md` 的分工：README 的后 2/3（816 行中的 260 行之后）是按时间倒序的
> 变更日志，适合查「某个功能是哪天怎么改的」；本文只讲**当前状态**的全貌与判断。

## 1. 一句话概括

这是一套**单机部署的运维控制台**，用来把一个 22 节点的鲲鹏 ARM64 计算集群
从「一堆裸机」带到「可用状态」，并在之后做日常监控与故障排查。

它不是通用的集群管理平台（不是 k8s、不是 Ansible 的替代品），而是**紧贴一套特定硬件
与网络规划**写的专用工具：子网划分、角色数量、网卡命名、磁盘规划都直接编码在代码里。

## 2. 它服务的那套集群长什么样

### 2.1 三平面物理隔离网络

三个平面走三套独立交换机，互不复用：

| 平面 | 带宽 | 子网 | 干什么用 |
|------|------|------|----------|
| 管理面 | GE | `172.16.0.0/24` | BMC / IPMI 带外管理 |
| 控制面 | 10GE | `172.16.3.0/24` | SSH、PXE 装机、心跳 |
| 数据面 DPDK-1 | 100GE | `200.1.1.0/24` | Master `eno2` 收数据 |
| 数据面 DPDK-2 | 100GE | `200.1.2.0/24` | Master `eno3` 收数据 |
| 数据面 RDMA-1 | 100GE | `100.1.1.0/24` | Master / Slave / SubSwath |
| 数据面 RDMA-2 | 100GE | `100.1.2.0/24` | Master / SubSwath / GStorage |

**「三平面」是贯穿全系统的第一概念** —— 数据模型、拓扑图、巡检、告警、诊断
全部按平面分维度组织。理解这套划分是读懂代码的前提。

### 2.2 节点角色

| 角色 | 台数 | 主机名 | 控制面 IP | 职责 |
|------|------|--------|-----------|------|
| PXE Host | 1 | `host-server` | 172.16.3.10 | DHCP/TFTP/HTTP/API，给其余节点装系统 |
| Master | 6 | `master-01~06` | .11~.16 | DPDK 收包 + RDMA 计算控制，100G×4 |
| Slave | 12 | `slave-01~12` | .51~.62 | RDMA 计算 + NFS 客户端，100G×1 |
| SubSwath | 2 | `subswath-01~02` | .170~.171 | NFS Server（4×7.68T NVMe RAID10） |
| GStorage | 1 | `gstorage-01` | .172 | NFS Server（机械盘硬件 RAID50） |

代码里还出现了 `acquisition`（采集）和 `sensor`（传感器）两个角色，
前者在 IP 规划页可配数量，后者只存在于演示种子数据里。

### 2.3 装机链路上还有一台 Windows

有一台 **Windows 管理站**跑本系统。PXE Host 自己也是裸机，
没法用 PXE 装自己，所以它的首次装机走另一条路：
Windows 管理站通过 BMC Redfish 把本地 ISO 挂成虚拟光驱，一次性 CD 引导。
这条路只在 PXE Host 首次部署时走一次。

## 3. 三条业务主线

系统的全部功能可以归成三块，对应三个截然不同的成熟度。

### 主线一：PXE 自动化部署（最完整的部分）

这是整个项目投入最多的模块 —— `api/pxe.py` 1025 行 + `PXEDeploy.vue` 2079 行，
是单文件规模最大的两处。

**完整链路：**

```
① IP 规划
   前端填各角色数量 → POST /api/pxe/network-plan
   → 按六子网固定方案算出全角色 IP 表（BMC / 控制面 / DPDK×2 / RDMA×2）

② 落成 nodes.json
   POST /api/pxe/nodes-json/regenerate
   → 生成 MAC → 节点配置 的映射表，存 backend/pxe_data/nodes.json
   → 合并逻辑会保留已填写的真实 MAC（_merge_nodes_json 按 hostname 对齐）
   → 现场用 PATCH /nodes-json/update-mac 把占位 MAC 换成实际 MAC

③ 生成装机配置（全部按需动态生成，不落盘）
   GET /api/pxe/dhcp-config         → dhcpd.conf
   GET /api/pxe/grub-config         → grub.cfg（aarch64 UEFI）
   GET /api/pxe/setup-raid1-script  → RAID1 初始化脚本
   GET /api/pxe/pxe-boot-script     → PXE 启动脚本

④ PXE Host 首次装机（Bootstrap，一次性）
   POST /api/pxe/pxe-host/install
   → RedfishClient.deploy_iso()：
       InsertMedia（挂 http://<windows>:8000/iso/xxx.iso）
       → BootSourceOverride=Cd/Once
       → ComputerSystem.Reset

⑤ 分批部署其余 21 台
   POST /api/pxe/wave-deploy/1  → SubSwath + GStorage
   POST /api/pxe/wave-deploy/2  → Master
   POST /api/pxe/wave-deploy/3  → Slave

⑥ 节点 firstboot 阶段自取配置
   GET /api/pxe/node-env?mac=<MAC>   → 纯文本 shell 变量，节点侧 source 后自配网络
   GET /firmware/manifest.json       → 按 lspci 匹配规则决定要不要刷固件
   POST /api/pxe/report              → 回报刷固件结果，写进 nodes.nic_firmware
```

**`node-env` 这个设计是整条链路的枢纽**：装机镜像本身完全通用，
节点差异（主机名、6 个平面的 IP、网卡名、大页数量、磁盘规划、NFS 挂载）
全部在 firstboot 时用自己的 MAC 回调 API 取回来。一套镜像装 22 台不同配置的机器。

**固件仓库**（`api/firmware.py`）是配套设施：按 `vendor/model/version/file` 分层存放
NIC/HBA/SSD 固件，`manifest.json` 写匹配规则（PCI vendor:device → 目标版本 → 烧写命令），
节点 firstboot 时自助比对升级。上传带 sha256 校验，路径分段做了白名单过滤。

### 主线二：集群管理与监控（**大部分是空壳**）

页面和 API 都在，但底下的实现基本是假的：

- **节点管理**（`api/nodes.py` + `Nodes.vue`）—— 真的。对 SQLite 的 CRUD，
  支持手动增删改节点和三平面网络信息。
- **组网图**（`api/network.py` 的 `/topology-graph` + `NetworkMap.vue` 744 行 D3.js）
  —— 拓扑**结构**是真的：从 DB 读节点、从 nodes.json 读每节点网卡清单，
  按四个平面（management / control / data_front / data_back）生成 nodes+links 喂给 D3 力导向图。
  但链路的**状态**取自 DB 字段，而 DB 字段没有任何东西在真实刷新。
- **网络连通性检查**（`POST /api/network/check/{node_id}`）—— 假的。
  返回硬编码：延迟 1.2ms / 0.5ms、吞吐 8500Mbps。
- **BMC/IPMI 管理**（`api/ipmi.py` + `services/ipmi_service.py`）—— **全部是假的**。
  子网扫描、BMC 信息、电源控制、设 PXE 引导、传感器读数，六个方法
  每一个都是「返回模拟数据 + 注释掉的实际实现」。注意这和主线一里
  **真实可用的 Redfish 客户端**是两套东西，不要混淆。
- **巡检**（`api/patrol.py` 296 行 + `Patrol.vue` 236 行）—— 代码写了，
  但前端路由被注释掉了，注释写着「暂未实现, 先想清楚交互再恢复」。
- **告警**（`api/alerts.py` + `Alerts.vue`）—— CRUD 和统计是真的，
  但 `/check-rules` 规则引擎判定的数据源同样来自没人更新的 DB 字段。

一句话：**这条线目前是「界面 + 数据结构」就绪，「数据采集」完全没做。**
没有任何常驻任务在轮询节点状态 —— `tasks/` 目录在 CLAUDE.md 里提到过，实际不存在。

### 主线三：故障诊断（第二完整的部分，真实可用）

`api/diagnose.py` 1635 行 + `Diagnose.vue` 1950 行。底层是 paramiko SSH，**是真的**。

前端三个标签页对应三种用法：

**① 业务诊断 / ② 硬件诊断**

把一批诊断脚本在一批节点上跑，自动判结论。核心设计是把「跑命令」升级成「判结论」：

```
DiagScript 表:
  script_content   要执行的命令/脚本
  target_node_type all / master / slave / sensor —— 限定适用角色
  expect_mode      exit_code      看退出码（默认）
                   fault_if_match stdout/stderr 命中正则 → 判异常
                   pass_if_match  命中正则 → 判正常，没命中 → 异常
  expect_pattern   上面用的正则（正则非法时自动退化为子串匹配）
  suggestion       判为异常时给运维看的处置建议
```

判定结果是三态而非两态：`pass` / `fail` / `error`。
`error` 专门用来区分「连接失败、超时、被取消」—— 这类情况**无法判定健康度**，
不能当成故障。这个区分在运维场景里很关键。

**一键体检**（`POST /scripts/batch-run`）把「选定脚本 × 选定目标」做笛卡尔积并发执行，
SSE 流式回报，前端汇总成体检报告。执行中可以 `POST /scripts/runs/{run_id}/cancel` 真终止。

种子数据预置了约 30 条脚本（`models/seed.py`），业务侧覆盖进程/服务状态，
硬件侧覆盖磁盘、内存、网卡、RDMA、DPDK、连接数等。

**③ 日志导出**

两种模式：

- `stdout` —— 脚本的 stdout 直接落成一个 `.log` 文件
- `files` —— 脚本的 stdout 是**一行一个远端绝对路径**，后端再走 SFTP 把这些文件整个拉回来。
  权限不足时兜底 `sudo cat`，同名文件自动加 `-2/-3` 后缀防覆盖。

**告警时间窗**是这条线上很实用的一个设计：传入 `alert_time` + 前后分钟数，
后端在脚本前自动插入

```sh
export ALERT_TIME='2026-05-15 03:24:11'
export ALERT_FROM='2026-05-15 03:14:11'
export ALERT_TO='2026-05-15 03:34:11'
```

脚本里直接 `journalctl --since "$ALERT_FROM" --until "$ALERT_TO"` 就能圈定故障时段的日志，
不用每次手改脚本。

**脚本库可移植**：支持导出/导入 JSON、导出成一个个 `.sh` 文件目录（带元信息头）再导回来、
以及 `save-bundle` 把当前脚本库固化进发布包，装到现场就自带脚本。

## 4. 技术架构

### 4.1 形态：单体，前端编译进后端

```
Vue 3 + Vite + Element Plus + D3.js
        │  npm run build → 输出到 backend/static/
        ▼
FastAPI（单进程）
  ├── /api/*        八个路由模块
  ├── /iso/*        StaticFiles，给 BMC 拉 ISO
  ├── /firmware/*   StaticFiles，给节点拉固件
  └── /{path:path}  SPA 兜底，返回 index.html
        │
        ▼
SQLite（单文件 cluster_manager.db）
```

开发模式下前后端分离，Vite 代理 `/api` 到 `:8000`；
生产模式下 Vite 直接把产物打进 `backend/static/`，FastAPI 同源提供服务。

**SPA 兜底路由有个坑已经踩过并修了**：`/{full_path:path}` 的贪婪匹配会优先于
FastAPI 的 `redirect_slashes`，把 `GET /api/nodes`（无尾斜杠）兜底成 HTML，
前端 axios 拿到 HTML 解析失败 → 节点表永远是空。
现在显式排除了 `api/`、`iso/`、`firmware/` 三个前缀。

### 4.2 四种运行方式，靠 config.py 统一

`config.py` 的 `_base_dir()` 解决「数据目录在哪」：

| 方式 | BASE_DIR 取值 |
|------|---------------|
| 开发 `python main.py` | `backend/` 目录 |
| PyInstaller 打包 | `sys.executable` 所在目录 |
| 部署包直接跑 | 同开发模式 |
| Docker | 环境变量 `CLUSTER_MANAGER_DATA` |

所有运行时路径（DB、pxe_data、static、iso、firmware）都从 BASE_DIR 派生。

还有个**桌面模式**（`desktop.py`）：后台起 uvicorn，前台用 pywebview 开原生窗口，
打包后双击 exe 不弹浏览器。冻结模式下日志重定向到文件。

### 4.3 数据模型（13 张表）

```
Node          节点主表 —— 三平面 IP/MAC/状态各一组，加 nic_firmware(JSON) 固件快照
NetworkLink   平面间链路 —— plane / protocol / 延迟 / 丢包 / 吞吐
BMCInfo       BMC 型号、版本、电源状态、温度、转速
Alert         告警，按 plane 分维度
PatrolRecord  巡检记录，按 plane 分维度
Log           日志，log_type = syslog/kernel/dpdk/rdma/bmc
FaultPoint    故障点 —— 关联日志 + 处置建议
DPDKStats     Master 侧收包统计
RDMAStats     Slave 侧收发统计
PXEConfig     PXE 网络配置
DiagScript    诊断脚本（本项目最有设计感的一张表，见主线三）
```

**迁移策略很朴素**：`main.py` 里一个 `_run_migrations()` 硬编码 `ALTER TABLE ADD COLUMN`
列表，逐条执行，`except: pass` 忽略「列已存在」。没有 Alembic。
好处是零依赖、部署简单；代价是只能加列，不能改列/删列/改类型。

## 7. 现状评估

这一节是通读代码后的判断，不是 README 的复述。

### 7.1 成熟度分层

```
可以直接用      PXE 配置生成 · Redfish 装机 · SSH 诊断与日志导出 · 固件仓库
界面好了但没数据  组网图状态 · 告警规则 · Dashboard 指标
纯占位          IPMI/BMC 全模块 · 网络连通性检查 · 日志采集 · 巡检
```

### 7.2 需要处理的具体问题

**① `pxe/` 目录是 v1 遗留，和 v2 冲突**

`pxe/pxe_setup.sh` 里 `PXE_SERVER_IP="192.168.1.10"`，而 v2 规划是 `172.16.3.10`。
`pxe/kickstart/*.ks` 用 `eth0/eth1/eth2` 三网卡、单个 `DATA_IP`，
而 v2 是 `eno1~eno5` + 六子网多 IP。

真正生效的 `dhcpd.conf` / `grub.cfg` 是 `pxe_service.py` **动态生成**的，
根本不走 `pxe/` 目录。这个目录现在的作用主要是误导读者。

**② kickstart 里有两处死引用**

```sh
curl -s http://{{PXE_SERVER}}:8000/agent/install.sh    # agent/ 下只有一个 Claude 对话记录
curl -X POST http://{{PXE_SERVER}}:8000/api/nodes/register  # 后端没有 register 端点
```

装机脚本真跑起来这两步会静默失败。

**③ `services/pxe_service_enhanced.py` 是死代码**

681 行，全仓库除了它自己没有任何引用。

**④ `wave-deploy` 名不副实**

`POST /api/pxe/wave-deploy/{1|2|3}` 读 nodes.json 把对应角色的节点写进 DB、
状态置为 `deploying` —— **仅此而已**。它不给节点上电、不设 PXE 引导、不触发任何实际动作。
真正的装机要靠节点自己网络启动。这个接口目前的语义是「标记这批节点进入部署中」，
不是「部署这批节点」。配合上 IPMI 模块全是模拟的，
**「一键分批部署」在当前代码里是走不通的**，还得人工去 BMC 上操作。

**⑤ 安全**

- `CORS allow_origins=["*"]` 配 `allow_credentials=True`
- SSH 密码明文存 `ssh_credentials.json`（有 `PWD_MASK` 但只是前端回显遮罩）
- BMC 密码明文存 `pxe_data/pxe_host.json`
- 全系统没有任何认证/鉴权，任何能访问 8000 端口的人都能控制集群

考虑到部署在内网管理站上，这些也许是可接受的取舍，但应该是**明确的决定**而不是遗漏。
（本仓库已把 `pxe_data/` 排除入库，源码里的硬编码默认密码也改成了读环境变量
`PXE_BMC_PASSWORD`，见 `backend/pxe_data_example/README.md`。）

**⑥ 没有任何测试**

全仓库零测试文件。考虑到核心逻辑里有 IP 规划算法、nodes.json 合并、
正则判定、SFTP 多文件下载这些**纯函数且易错**的部分，这是比较可惜的 —— 
这几处恰好是最适合单测、收益最高的地方。

**⑦ README 结构失衡**

816 行里 557 行是变更日志。新人打开 README 先撞上的是时间线而不是全貌。
（本文试图补上这个缺口。）

### 7.3 如果要继续做，优先级建议

1. **把 IPMI 做成真的** —— 它是「⑤ 分批部署」能否闭环的前提。
   项目里已经有一个能用的 `RedfishClient`，扩展它比补 ipmitool 更顺。
2. **加一个状态采集的常驻任务** —— 现在所有状态字段没人写，
   组网图/告警/Dashboard 全部悬空。哪怕先做最简单的 ping + SSH 探活。
3. **清理 v1 遗留** —— 删掉或明确标注 `pxe/` 目录和 `pxe_service_enhanced.py`，
   修掉 kickstart 里的两处死引用。
4. **给纯函数补测试** —— IP 规划、nodes.json 合并、`_evaluate_verdict`。
5. **决定巡检模块的去留** —— 要么接上路由，要么删掉那 532 行。

## 8. 快速上手

```bash
# 后端
cd backend
pip install -r requirements.txt
python run.py                 # 或 uvicorn main:app --reload --port 8000
# 启动时自动完成：建表 → 列迁移 → 种子数据 → 预生成 pxe_data/nodes.json
# Swagger: http://localhost:8000/docs

# 前端
cd frontend
npm install
npm run dev                   # http://localhost:3000，/api 代理到 :8000
npm run build                 # 产物直接输出到 backend/static/
```

首次部署需要准备 `pxe_data/`（含敏感信息，不入库）：

```bash
mkdir -p backend/pxe_data
cp backend/pxe_data_example/nodes.json.example    backend/pxe_data/nodes.json
cp backend/pxe_data_example/pxe_host.json.example backend/pxe_data/pxe_host.json
export PXE_BMC_PASSWORD='your-bmc-password'
```

### 8.1 打包成独立 App

`build_app.py` 是唯一的构建入口（跨平台）。它把前端 + 后端打成一个不依赖
Python / Node 的可执行目录，并压缩成发布包：

```bash
python build_app.py                  # 自动：Windows→desktop，其他→server
python build_app.py --mode desktop   # pywebview 原生窗口，双击 exe 不弹浏览器
python build_app.py --mode server    # uvicorn 控制台进程，浏览器访问
```

| 步骤 | 做的事 |
|------|--------|
| 1 环境检查 | node / npm / python 是否齐，desktop 模式校验 pywebview 可导入 |
| 2 前端 | `npm run build` → `backend/static/`（`--skip-frontend` 可复用已有产物） |
| 3 依赖 | `pip install -r requirements.txt` + pyinstaller（`--skip-deps` 跳过） |
| 4 打包 | PyInstaller 按 `CLUSTER_MANAGER_BUILD_MODE` 选入口：desktop→`desktop.py`，server→`main.py` |
| 5 资源 | 复制 `static/`、`scripts_bundle.json`、`pxe_data_example/`，建空 `iso/` `firmware/`，写启动脚本 |
| 6 自检+打包 | server 模式拉起产物打一次 `/api/nodes` 确认能跑，然后 zip / tar.gz |

两个关键点：

- **`static/` 不进 PyInstaller bundle**，而是复制到 exe 旁边。`config.py` 的
  `BASE_DIR = dirname(sys.executable)`，这样现场换前端文件不用重新打包。
- **默认不打包真实 `pxe_data/`**，只带 `pxe_data_example/`。`pxe_host.json` 里有
  BMC 明文口令，打进分发包等于把凭据发出去；确实需要时用 `--include-pxe-data`。

`build.bat` / `build.sh` 保留为薄封装（分别转发 `--mode desktop` / `--mode server`），
参数原样透传。`.github/workflows/build-app.yml` 在 windows + ubuntu 两个 runner 上跑
同一个脚本，产物挂在 Actions 的 Artifacts 里，打 `v*` tag 时自动发 Release。

其余生产部署方案（Docker 多平台 / deploy.sh 部署包）见 `README.md` 的「生产部署」一节。
